## 最適化の主目的
この作業の主目的は、推論時の計算速度を向上させることである。

特に以下を通じて高速化を目指す。

- force feature の完全な行列 `(3N, N_feat)` を実体化しない
- 特徴量次元を C++ 内で早期に縮約する
- Python 側での大きな行列演算・後処理を減らす
- メモリ使用量とメモリアクセス量を削減する
- 既存の `infer_Cul_F2_R.py` による旧推論経路より高速な推論を目指す

ただし、高速化は数値的一致性を保ったうえで達成すること。
速度向上のみを優先して、数式・特徴量順序・符号規約・力の定義を変えてはならない。
## パスと参照位置に関する注意
既存スクリプト群は、現在の作業ディレクトリ構成と参照位置がずれている可能性がある。

特に以下を実装前に確認すること。

- `train_Cul_F2_R.py` から参照している入力ファイル・出力ファイルの位置
- `infer_Cul_F2_R.py` から参照しているモデル、POSCAR、モジュールの位置
- `build/build_descriptor_R.py` が参照している C++ ソースの位置
- ビルド後の `.so` / 拡張モジュールの出力位置
- `tests/test_all2_R.py` から参照する必要がある POSCAR / `.npz` / モジュールの位置

重要事項:
- まず参照パスの整合性を確認し、その後に実装変更を行うこと
- パス修正は必要最小限にとどめること
- ロジック変更とパス変更を同時に大規模実施しないこと
- 旧スクリプトの比較可能性を失わないこと
# プロジェクト: descriptor_all2_R の推論最適化

## 目的
`descriptor_all_R.cpp` をもとに、推論専用の最適化版 `descriptor_all2_R.cpp` を作成する。

最適化の目標は次のとおり。

- 力特徴量の完全な行列 `(3N, N_feat)` を実体化しない
- 線形モデル係数を Python から C++ に渡す
- 特徴量次元の縮約を、数式的に安全な最も早い段階で C++ 内で行う
- 最終的なエネルギーと力を直接返す

## 既存スクリプトとの関係
この作業は既存の Python ワークフローを前提とする。

### 既存の学習スクリプト
- `train_Cul_F2_R.py`
  - 線形モデルの学習・保存を行う既存スクリプト
  - 学習済み係数や関連データの保存形式を確認する際の参照元とする
  - 新しい推論モジュールの入力係数 `coef_py` は、この学習スクリプトの出力と整合している必要がある

### 既存の推論スクリプト
- `infer_Cul_F2_R.py`
  - 現在の推論フローを実行する既存スクリプト
  - 旧経路の参照実装として扱う
  - 新しい `descriptor_all2_R` は、可能な限りこの既存推論フローに自然に組み込める設計にする
  - 必要なら `infer_Cul_F2_R.py` を参考にして、新モジュール用の最小差分推論コードまたは検証コードを作る

## 重要なルール
1. 元の数式・数学的内容を厳密に保つこと。
2. 特徴量の順序とインデックス規約を厳密に保つこと。
3. 符号規約を黙って変更しないこと。
4. 必要がない限り、ファイル全体を書き直さないこと。
5. 変更はできるだけ最小限かつ局所的にすること。
6. 元の `descriptor_all_R.cpp` は参照実装として保持すること。
7. これは学習系の改修ではなく、推論専用の最適化として扱うこと。
8. 旧パイプラインとの数値検証を必須とすること。

## 対象ファイル
- 元ソース: `src/descriptor_all_R.cpp`
- 新ソース: `src/descriptor_all2_R.cpp`
- 旧ビルドスクリプト: `build/build_descriptor_R.py`
- 新ビルドスクリプト: `build/build_descriptor2_R.py`
- 検証スクリプト: `tests/test_all2_R.py`
- 既存学習スクリプト: `train_Cul_F2_R.py`
- 既存推論スクリプト: `infer_Cul_F2_R.py`

## 想定する API の方向性
新しい pybind モジュール `descriptor_all2_R` は、可能な限り旧実装と近い構造入力インターフェースを維持しつつ、追加で以下を満たすこと。

- Python から `coef_py` を NumPy 配列として受け取ること
- 係数長を内部の特徴量次元と照合すること
- 次元不一致の場合は、明確なエラーメッセージで停止すること

## カーネル変更の目標
内部計算を次のように改修すること。

- 特徴量ごとの力出力 `(3N, N_feat)` を実体化しないこと
- `coef[kfeat]` との縮約を、数式的に安全な最も早い段階で行うこと
- 必要なら `lambda_compact[...]` のような縮約済みのコンパクトなバッファを使うこと
- 最終的な力出力は、できれば `(N, 3)` にすること

## 既存ワークフローに対する位置づけ
新規実装は、既存の学習・推論資産を壊さずに追加する。

- `train_Cul_F2_R.py` の出力形式は原則として変更しない
- `infer_Cul_F2_R.py` の旧経路は比較対象として維持する
- 必要であれば、新しい推論経路を試すための最小差分版スクリプトを別途作成してよい
- ただし既存スクリプトを大きく書き換える前に、まず `descriptor_all2_R.cpp` 単体の正しさを確認する

## 検証要件
`tests/test_all2_R.py` では、以下の2経路を比較すること。

### 旧経路
- 旧モジュールで descriptor / force feature を計算する
- Python 側で係数を掛ける
- 必要なら `infer_Cul_F2_R.py` の計算手順・データ読込方法を参照する

### 新経路
- `descriptor_all2_R` に係数を直接渡して計算する

### 比較項目
- エネルギー
- 力
- 出力 shape
- 最大絶対誤差
- RMSE

## 実装方針
1. `descriptor_all_R.cpp` を調査し、`kfeat` がどこで生成・反復されているかを特定する。
2. `infer_Cul_F2_R.py` を確認し、旧推論フローでどの出力が最終的にエネルギー・力へ変換されているかを把握する。
3. `train_Cul_F2_R.py` を確認し、学習済み係数の保存形式・読み込み形式・shape を把握する。
4. `coef[kfeat]` の縮約を、安全な最も早い位置で融合する。
5. OpenMP 構造がある場合は維持する。
6. 不要な巨大一時配列は作らない。
7. 縮約を融合した箇所にだけ、簡潔なコメントを追加する。

## やってはいけないこと
- 明示的な必要がない限り、規約を変更しないこと
- 旧経路との比較可能性を損なわないこと
- アルゴリズム自体を別設計に置き換えないこと
- `train_Cul_F2_R.py` の保存形式を無断で変えないこと
- `infer_Cul_F2_R.py` をいきなり全面改修しないこと
- コンパイル成功だけで終了しないこと。数値検証まで必須

以下をすべて満たしたときに完了とみなす。

3. 新経路で完全な `(3N, N_feat)` を実体化しないこと
4. エネルギーと力の出力が、旧経路と厳しい許容誤差内で一致すること
5. `train_Cul_F2_R.py` の出力係数と新モジュールの入力が整合していること
6. 必要に応じて `infer_Cul_F2_R.py` の旧結果と新結果が比較できること
7. もし不一致が残る場合は、その原因候補を明示的に記録すること
8. 旧推論経路と新推論経路の実行時間を比較し、高速化の有無を報告すること
